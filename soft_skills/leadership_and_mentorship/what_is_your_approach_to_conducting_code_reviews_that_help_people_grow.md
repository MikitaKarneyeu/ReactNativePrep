Code reviews are one of the highest-leverage opportunities for mentorship. My approach is to treat every review as a teaching and learning opportunity, not just a quality gate.

I start by reviewing the intent before the implementation. I read the PR description and linked ticket to understand what the code is trying to accomplish. This helps me evaluate whether the implementation achieves the goal, rather than just nitpicking syntax. If the PR description is missing or unclear, I ask for it—this teaches the importance of documenting intent.

When I find issues, I categorize them and respond accordingly. For bugs or correctness issues, I'm direct and specific: "This will throw a null reference if the user has no orders—here's the scenario." For design or architecture concerns, I ask questions rather than dictate: "Have you considered using a strategy pattern here? If we add more payment types later, this switch statement will grow significantly." For style or convention issues, I point to the team's style guide or existing patterns: "We use `const` by default—see our ESLint config. This is a minor change but helps us stay consistent."

I also invest time in explaining the "why" behind my feedback. A junior developer who hears "don't use `any` in TypeScript" learns a rule. A junior developer who hears "using `any` disables the type checker, which means the compiler can't catch type errors at build time. Since this function handles user data, we want the compiler to catch incorrect data shapes before they reach production" learns a principle. I link to relevant articles, documentation, or examples when a concept deserves deeper exploration.

I balance criticism with genuine acknowledgment of good work. If someone implemented a clean abstraction, wrote thorough tests, or handled an edge case I wouldn't have thought of, I say so. Positive feedback reinforces good practices and makes constructive criticism easier to receive. I also adapt my level of detail based on the reviewer's experience—a senior developer gets high-level architectural feedback, while a junior developer gets more detailed guidance on patterns and best practices.
