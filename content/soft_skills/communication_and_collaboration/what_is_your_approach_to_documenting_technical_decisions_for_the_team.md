I use Architecture Decision Records (ADRs) as my primary tool for documenting technical decisions. An ADR is a short document that captures the context, the decision, and the consequences. The format is simple: title, status (proposed/accepted/deprecated), context (what problem we're solving and what constraints exist), the decision itself, and the consequences (both positive and negative).

For example, when our team debated whether to use REST or GraphQL for a new service, I wrote an ADR that laid out the context: "We're building a mobile-first API consumed by three different client applications with varying data needs." The decision section documented our choice (GraphQL) and why, along with trade-offs we accepted (steeper learning curve, more complex caching). This became a reference point months later when a new team member asked why we didn't use REST—they could read the full reasoning instead of relying on memory or Slack archaeology.

I keep ADRs in the repository alongside the code, typically in a `/docs/decisions` folder. This has two advantages: decisions are version-controlled and they live close to the code they affect. When someone opens a PR that contradicts a previous decision, reviewers can reference the ADR and discuss whether the context has changed.

For smaller, day-to-day decisions that don't warrant a full ADR, I use code comments, PR descriptions, and commit messages to capture the "why." I follow the principle that future developers (including my future self) need to understand the reasoning, not just the outcome. A PR description that says "Refactored auth to use JWT" is far less useful than one that says "Switched from session-based auth to JWT because our microservices need stateless authentication and the mobile team can't maintain session cookies." The goal is always to make the decision-making process discoverable.
