When reviewing code with significant issues, I balance honesty with empathy. The goal is to fix the problems while preserving the author's motivation and helping them improve. My approach is to be direct about the issues, constructive about the solutions, and respectful of the person.

First, I categorize the issues by severity. Critical issues (bugs, security vulnerabilities, data loss risks) must be fixed before merging—I'm unambiguous about these. Architectural or design issues (wrong abstraction, tight coupling, violation of patterns) are significant but may have nuance—I present my concerns with reasoning and alternatives. Style or convention issues are minor—I note them but don't let them overshadow the bigger picture.

For significant issues, I start by acknowledging what the code does well or what the author was trying to accomplish. This isn't empty flattery—it signals that I've engaged with the code thoughtfully and that my feedback is about the code, not the person. Then I present the issues clearly: "There are a few concerns I'd like to discuss before we merge this. The main one is that the data access logic is mixed into the controller, which will make it hard to test and reuse. Here's what I'm thinking—let me know your perspective."

I frame feedback as questions or suggestions rather than commands when possible. Instead of "Rewrite this using the repository pattern," I say "Have you considered extracting the data access into a repository? It would make the controller easier to test and align with our existing patterns." This invites discussion rather than creating defensiveness, and sometimes the author has good reasons for their approach that I haven't considered.

If the code needs a substantial rewrite, I suggest a pair-programming session rather than just leaving a list of comments. Working together is faster and more educational than a back-and-forth review cycle. I also offer to explain the patterns or approaches I'm recommending—not everyone has the same background, and what's obvious to me might be new to them. The goal is to turn a difficult review into a learning opportunity that makes the author better, not to make them feel bad about their code.
