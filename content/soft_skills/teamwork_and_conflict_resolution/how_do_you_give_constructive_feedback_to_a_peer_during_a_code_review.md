Code review feedback should be helpful, specific, and respectful. My goal is to improve the code and help the author grow, not to demonstrate my own expertise or enforce personal preferences. I follow several principles that have served me well.

First, I distinguish between must-fix issues and suggestions. For bugs, security issues, or correctness problems, I'm direct: "This will cause a null pointer exception if the user has no profile—here's the scenario." For style preferences or alternative approaches, I frame them as suggestions: "Consider using `Array.find` here instead of a loop—what do you think?" This lets the author decide whether to act on subjective feedback without feeling micromanaged.

Second, I explain the "why" behind my feedback. Instead of just saying "don't use `any` here," I say "Using `any` bypasses TypeScript's type checking, which means we won't catch type errors at compile time. Since this function handles financial data, I'd recommend typing this as `Transaction` so the compiler can catch misuse." This turns feedback into a learning opportunity and helps the author make better decisions independently in the future.

Third, I balance criticism with acknowledgment. If the author implemented a clever solution or wrote clean tests, I say so. A review that's entirely negative is demoralizing and makes people dread the process. Even a brief "Nice use of the strategy pattern here—makes this much more extensible" goes a long way.

I also pay attention to tone. Written feedback lacks vocal inflection, so words like "obviously" or "just" can come across as dismissive. I avoid phrases like "This is wrong" and instead say "I think there might be an issue here—have you considered X?" I also avoid drive-by reviews where I only nitpick formatting while missing the bigger picture. I make sure to review the overall design and logic first, then address smaller issues. The best code reviews leave the author feeling supported, not attacked.
