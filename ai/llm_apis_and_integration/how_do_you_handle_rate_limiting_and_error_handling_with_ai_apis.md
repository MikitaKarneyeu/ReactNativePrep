Rate limiting is a critical concern when using AI APIs—providers enforce limits on requests per minute (RPM) and tokens per minute (TPM) to ensure fair usage and system stability. When you exceed limits, you receive 429 (Too Many Requests) errors. Handling these gracefully is essential for production applications.

Implement exponential backoff with jitter for retries. When a 429 error occurs, wait before retrying—start with a short delay (1 second), then double the wait time for each subsequent retry (2s, 4s, 8s, 16s), adding random jitter to prevent thundering herd problems. Most providers include `retry-after` headers indicating how long to wait. Set a maximum retry count (typically 3-5) to prevent infinite loops.

Proactive rate limit management includes tracking your usage against limits, queuing requests when approaching limits, and distributing requests across time. Implement request queuing with configurable concurrency—limit the number of simultaneous API calls to stay within RPM limits. Use token counting to estimate TPM usage before making requests. Some applications implement token bucket algorithms to smooth out request patterns.

Comprehensive error handling should cover multiple failure modes. Network errors (timeouts, connection failures) require retries with backoff. Authentication errors (401, 403) require API key validation without retry. Server errors (500, 502, 503) are transient and should be retried. Content filter errors (400 with specific error codes) require prompt modification without retry. Context length errors require prompt truncation. Implement circuit breaker patterns—if errors exceed a threshold, temporarily stop sending requests to avoid wasting resources.

For production systems, implement fallback strategies. Use multiple API providers—if OpenAI is rate-limited, fall back to Anthropic. Cache responses for repeated queries. Use smaller, cheaper models for simple requests, reserving expensive models for complex tasks. Monitor error rates and set up alerts. Log all API interactions for debugging and cost tracking. In distributed systems, use a centralized rate limiter (Redis-based) to coordinate across multiple application instances.
